# 폐쇄망 적용 절차 (2026-09-26) — 배포 ⑤ 새 대시보드

> 대상: 전체 작업순서 **F단계(대시보드 개편 9-2)** 전체 + F4-1(보이지 않는 메뉴 조회 정지) + 성능 이력 Top 세션 11g 수정
> 배포 ①~④를 아직 적용하지 않았다면 이번 jar에 모두 포함되어 있다. 배포 ② 절차서의 2절(sqlrestapi prompt 복사)만 추가로 하면 된다.
> 적용 내용: **jar 교체만.** DB 파일은 앱이 기동할 때 새 테이블 5개(`mon_*`)를 스스로 만든다. 설정 키는 전부 선택(없으면 기본값).

## 무엇이 바뀌나

| 구분 | 내용 |
|---|---|
| 대시보드 | 우측 하단 스위치의 **첫 번째 버튼이 새 대시보드**(예전 게이지·탭 화면을 대체). 두 번째 버튼(v2)은 그대로 |
| ① KPI | 현재·구간 평균·최대 AAS, CPU 코어 초과 분 수, **활성 세션**, **메모리 사용률**(숫자 아래 작은 막대) |
| ② 차트 | 대기 클래스 8분류 누적 영역 + CPU 코어 기준선. 클릭(5분)·드래그로 구간 선택, "표로 보기" |
| ③ Lock | TX/TM 대기 실시간(리프레쉬 3초), 60초↑ 블로킹 TM Holder 6개↑면 **장애** → 관리자는 "장애 처리"로 Holder KILL(확인 패널, 감사 기록) |
| ④ 진단 | 선택 구간에서 가장 큰 대기 클래스와 조치 문구 |
| ⑤⑥⑦ | 선택 구간 Top SQL·세션·대기 이벤트 → 클릭하면 오른쪽 상세 창(세션/SQL/이벤트, KILL 구문 복사) |
| ⑧ 점검 알림 | 테이블스페이스(97/98%)·FRA·TEMP(10분), 잡 실패(30분), 테이블 용량·무효 객체·통계(매일 03시 + 기동 직후) |
| 부하 | 대시보드만 띄워 두면 다른 메뉴(Lock Tree·Current Session·성능 이력) 조회가 더는 원본 DB로 나가지 않음. Lock 조회는 여러 명이 봐도 DB별 주기당 1회 |
| 버그 | 성능 이력 조회 Top 세션이 **11g에서 ORA-00933**으로 실패하던 문제 수정 |
| 화면 배율 | 배포 ②의 80%를 **90%로 되돌림**(모든 화면 통일 유지 — 80%는 글씨가 작아 구분이 어려웠음), ②③ 차트 행 높이 고정 |

## 1. 앱 jar 교체

```bash
./stop-aix.sh
ps -ef | grep dbagent-java | grep -v grep        # 아무것도 안 나와야 정상
cp -p dbagent-java-0.1.0.jar dbagent-java-0.1.0.jar.bak-$(date +%Y%m%d-%H%M)
cp -rp db_config db_config.bak-$(date +%Y%m%d-%H%M)   # 새 테이블이 생기므로 DB 파일도 백업(롤백용)
cp <반입한 jar> dbagent-java-0.1.0.jar
./start-aix.sh
```

## 2. 수집 계정 권한 확인 (⑧ 점검용)

⑧ 점검은 `dba_*` 딕셔너리 뷰를 읽는다. 권한이 없으면 그 항목은 **회색 "점검 실패" 카드**로 보인다(알림 없음으로 숨지 않음).

```sql
-- 수집 계정으로 접속해 확인 (0이 아니면 됨)
SELECT COUNT(*) FROM dba_tablespace_usage_metrics;
SELECT COUNT(*) FROM dba_scheduler_job_run_details WHERE ROWNUM = 1;
-- 권한이 없으면 DBA가: GRANT SELECT_CATALOG_ROLE TO <수집 계정>;
```

KILL은 관리자 화면에서만 가능하며 수집 계정에 `ALTER SYSTEM` 권한이 있어야 실제로 실행된다(없으면 결과가 FAILED로 감사 기록에 남음).

## 3. 새 설정 키 (선택, `dist/application.properties.sample`에 전체 목록)

| 키 | 기본값 | 설명 |
|---|---|---|
| `dbagent.monitor.tm-holder-last-call-et-seconds` | 60 | TM Lock 장애 판정 last_call_et 기준(배포 ①) — 새 대시보드·v2 공통 |
| `dbagent.monitor.tm-holder-incident-count` | 6 | 장애 판정 Holder 수 |
| `dbagent.monitor.tm-holder-kill-blocking-only` / `-inactive-only` | false | KILL 대상 좁히기(기본은 USER Holder 전체) |
| `dbagent.monitor.check-daily-hour` | 3 | 무거운 점검 실행 시각(시). 기동 직후에도 1회 |
| `dbagent.monitor.check-interval-minutes` / `check-job-interval-minutes` | 10 / 30 | 가벼운 점검 / 잡 실패 점검 주기(분) |
| `dbagent.monitor.check-tablespace-warn-pct` / `crit-pct` | 97 / 98 | 테이블스페이스 임계치 |
| `dbagent.monitor.check-table-size-warn-gb` / `crit-gb` | 30 / 40 | 테이블 용량 임계치 |
| `dbagent.monitor.check-fra-*`, `check-temp-*` | 80/90, 75/90 | FRA·TEMP 임계치 |
| `dbagent.monitor.check-exclude-owners` | SYS,SYSTEM,AUDSYS,XDB,MDSYS,CTXSYS | 점검 제외 스키마 |
| `dbagent.monitor.store-retention-days` / `kill-audit-retention-days` | 30 / 365 | `mon_*` 보관 기간 |
| `dbagent.monitor.ash-awr-fallback` | true | Diagnostics Pack 없으면 false(배포 ④) |

> 1일 점검 쿼리 타임아웃(`check-daily-query-timeout-seconds`, 120)은 `dbagent.oracle.read-timeout-ms`(60000)보다 5초 짧게 **자동으로 제한**된다. 큰 DB에서 테이블 용량 점검이 "점검 실패(타임아웃)"로 나오면 두 값을 같이 올린다.

## 5. 현장 실측 부탁

| 항목 | 방법 | 이유 |
|---|---|---|
| 11g DB에서 `/top` 한 번 스캔 | 11g 인스턴스에서 새 대시보드 ⑤⑥⑦가 뜨는지 + (가능하면) `/top` 쿼리 EXPLAIN에 `TEMP TABLE TRANSFORMATION` | 21c에서만 확인됨 |
| 1일 점검 소요 시간 | 기동 1~2분 뒤 ⑧에 테이블 용량·무효 객체·통계 항목이 "점검 실패(타임아웃)"로 나오는지 | 큰 DB의 `dba_segments` 스캔 시간 |
| SQL 통계 수집 시간 | 앱 로그에 `sqlstat delta collection for db_id=... took` 경고(5초 이상)가 있는지 | 공유 풀이 큰 DB의 `v$sqlstats` 스캔 시간 |
| 스케줄러 이력 크기 | `SELECT table_name, num_rows FROM dba_tables WHERE table_name IN ('SCHEDULER$_JOB_RUN_DETAILS','SCHEDULER$_EVENT_LOG');` | 잡 실패 점검이 이 두 테이블을 매번 전체 읽음(30분 주기) |
| RAC 등록 방식 | DB 관리에서 RAC 노드가 서비스명(`connect_mode=service`)으로 등록된 항목이 있는지 | 배포 ③ 안내와 같음 |

```bash
./stop-aix.sh
```
